# Reasoning and Mission Planner

This first implementation turns a natural-language mission and a supplied world
snapshot into candidate tasks using Google AI Studio's Gemini Developer API.
It follows the existing [Mission Orchestrator input](../mission-orchestrator/SKILL.md#input).

The planner decomposes goals and task dependencies. The orchestrator owns robot
allocation, action selection, robot-level sequencing and execution recovery.
The [connected pipeline](PIPELINE.md) adds a minimal Mission Interface gate and
invokes the existing orchestrator skill to produce a validated dispatch plan.

## Setup

From the repository root, install the locked environment with [uv](https://docs.astral.sh/uv/):

```bash
uv sync --locked
cp .env.example .env
```

Set `GEMINI_API_KEY` in `.env` to a key created in
[Google AI Studio](https://aistudio.google.com/apikey). `.env` is ignored by Git.
The CLI also accepts `GOOGLE_API_KEY` if `GEMINI_API_KEY` is unset or empty.
Existing environment variables take precedence over `.env`.

`GEMINI_MODEL` defaults to `gemini-3.5-flash-lite`, which Google lists with a free
tier. Set it or pass `--model` to use another text-generation model your
key can access. Record the selected model for reproducible experiments.

For free-tier-only testing, use a project with billing disabled. The code cannot
inspect billing status or remaining shared project quota from an API key. Local
request limits reduce usage; they do not make requests free on a billed project.
Quota errors stop the run without a retry or a fallback to a different model.
Token counts reported by completed responses are printed on stderr, separately
from the candidate JSON. They do not report the project's remaining quota.
Check your project tier and limits in [AI Studio](https://aistudio.google.com/projects)
and Google's [pricing](https://ai.google.dev/gemini-api/docs/pricing).

## Run

For the full reasoning → interface → orchestration → dispatch-validation flow, use
[run_mission.py](PIPELINE.md). The commands below run only the reasoning stage.

Inspect the planning context and output schema without making an API call:

```bash
uv run python reasoning-layer/plan_mission.py \
  --input reasoning-layer/examples/request.json --dry-run
```

Generate a candidate handoff using the same mission/world as the orchestrator example:

```bash
uv run python reasoning-layer/plan_mission.py \
  --input reasoning-layer/examples/request.json \
  --output outputs/mission-001.json
```

Omit `--output` to print a ready handoff as JSON on stdout. Output paths must be new:
the CLI refuses to overwrite an existing file, including after an unsuccessful run.
Use a new filename for the next experiment. `outputs/` is ignored by Git.

To try your own mission, copy `examples/request.json` and edit `natural_language`
and the known world. Requests have exactly `mission_id`, `natural_language`, and
`world`. Fleet capabilities are loaded afresh from `mission-orchestrator/robots.json`,
or the path passed with `--fleet`. The API receives that mission, world and fleet;
it receives no robot-control tools.

## Handoff contract

A ready candidate has exactly the orchestrator's three top-level fields:

```json
{
  "mission_id": "M-001",
  "tasks": [
    {
      "task_id": "T1",
      "description": "Locate the apple in the kitchen",
      "depends_on": [],
      "constraints": {}
    }
  ],
  "world": {
    "entities": {
      "kitchen": {"kind": "room"},
      "apple": {"kind": "object"}
    },
    "robots": {"drone_1": {"at": "kitchen", "airborne": true}}
  }
}
```

`mission_id` and `world` are copied from the request, never generated by Gemini.
World extension fields are preserved. Each task contains `task_id`, `description`,
`depends_on`, and a JSON object `constraints`; dependencies refer to task IDs.
No assignments, robot actions or dispatch steps are accepted at task level.
The output schema is included in the model's instructions, with inline task definitions.
This initial adapter uses text generation plus strict local JSON validation;
it does not rely on provider-enforced structured output. Native schema requests
returned HTTP 400 during integration testing with the supplied free-tier project.
Generated constraints use `{"requirements": ["..."]}` (or `{}`),
which fits the orchestrator's existing free-form constraints object. Strict local
validation remains authoritative, including rejection of extra task fields.
`examples/expected_handoff.json` is a reference fixture, not a recorded Gemini result.

Internally Gemini returns `status`, `tasks`, `questions`, and `reasons`. Only
`ready` can become a handoff. `needs_clarification` and `infeasible` print a decision
report instead and never create an output file.

| Exit code | Meaning |
| --- | --- |
| 0 | Candidate produced, or dry run completed |
| 2 | Input/configuration/API/output error or invalid generated task contract |
| 3 | Clarification needed or mission judged infeasible; no handoff |

## Checks and limits

- Strict field/type checks, unique task IDs, known dependencies and an acyclic task graph.
- World shape/reference checks before calling Gemini.
- One generation call by default, capped at 2048 output tokens and 30000 prompt
  characters (system/context/schema combined). Configure `--max-output-tokens`
  (128–8192) and `--max-prompt-chars` (1000–100000) for larger scenarios.
- `--max-attempts 2` explicitly enables one repair for invalid JSON/tasks.
  No automatic HTTP retries; timeout is 45 seconds
  per call, configurable with `--timeout-ms` (1000–120000).
- Empty, blocked and truncated provider responses fail without producing a handoff.
- Raw provider exceptions and API keys are not printed by the application.

These checks establish structural compatibility, not semantic correctness, physical
feasibility, or mission success. Unsupported/ambiguous goals are addressed by the
model prompt and decision statuses; validate them on your real scenario set.
The orchestrator is an agent skill plus a dispatch-plan validator. `plan_mission.py`
only generates a candidate; `run_mission.py` invokes the orchestrator through
Gemini and validates its dispatch plan. Neither sends robot commands.
Execution-feedback ingestion and preserving completed work during
mission-level replanning are future work; do not use this initial CLI to restart
an active mission from its original request.

## Tests

```bash
uv run python -m unittest discover -s reasoning-layer/tests -t reasoning-layer -v
uv run python mission-orchestrator/validate_plan.py \
  mission-orchestrator/examples/dispatch_plan.json
```

The offline tests mock only Gemini's responses and exercise the real contract,
planner, SDK request configuration and CLI. The integration check passes the
reference candidate's world into the existing dispatch validator and verifies
task-ID correspondence with the existing dispatch example. It does not demonstrate
that arbitrary generated tasks can be orchestrated successfully.

## Files

- `plan_mission.py`: command-line entry point.
- `run_mission.py`: connected pipeline entry point; see [pipeline usage](PIPELINE.md).
- `reasoning/interface.py`: initial handoff validation gate.
- `reasoning/orchestration.py`: runtime adapter for the existing skill and validator.
- `reasoning/pipeline.py`: connects the planning stages.
- `reasoning/contracts.py`: request, decision and task validation.
- `reasoning/planner.py`: provider-independent planning and handoff construction.
- `reasoning/gemini.py`: official Google Gen AI SDK adapter.
- `reasoning/system_prompt.txt`: mission reasoning and ownership rules.
- `examples/`: input mission and expected contract fixture.
- `tests/`: offline checks; no key or network calls needed.

API references: [Google Gen AI SDK](https://googleapis.github.io/python-genai/),
[structured outputs](https://ai.google.dev/gemini-api/docs/structured-output),
and [API keys](https://ai.google.dev/gemini-api/docs/api-key).
